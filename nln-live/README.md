## Production requirements

The Blueprint at `nln-live/render.yaml` attaches the EXISTING Render Postgres database named `nln-database`. It creates a new **free web service** but does not modify the legacy routing server. Plan and review it before approval. The new web service needs successful database health and form-submission tests.

### Important free-web-service caveat
Render free web instances spin down after inactivity. Their `robots.txt` endpoint can return a temporary disallow-all during spin-down. Move the marketing site to reliable always-on hosting before enabling public search indexing. The existing paid NLN Postgres DB is retained.

### Switches
- `SEARCH_INDEXING_ENABLED=false` by default: keeps site out of search results.
- `SITE_URL`: set to the verified owned domain, e.g. `https://<your-domain>`, **after** purchase/ownership confirmation and DNS linking.
- `INTAKE_OPEN=true`: enable only when the database connection is healthy.
- `ADMIN_KEY`: generated by Render and stored in service environment; do not commit it or email it.
- `GSC_VERIFICATION_TOKEN`: fill using the exact meta content generated by Google Search Console.
- `RESEND_API_KEY`, `LEAD_FROM_EMAIL`, `LEAD_NOTIFY_EMAIL`: optional email notification via verified account; not needed for inbox.
- `PGSSL=true`: optional for environments requiring SSL.

### Search Console
1. Configure the owned domain through the Render dashboard.
2. Verify `https://domain/` works with TLS, real inquiry form and inbox, privacy notice, mobile layout.
3. Add the Google-provided verification value to `GSC_VERIFICATION_TOKEN` or use DNS TXT verification with the registrar.
4. After indexing readiness sign-off, set `SITE_URL` and `SEARCH_INDEXING_ENABLED=true`.
5. Check `/robots.txt`, `/sitemap.xml`, and live response headers.
6. Submit sitemap in Search Console. Google does not guarantee indexing or ranking.

## Fixed-price package purchase funnel (staging, November 21, 2026)

The canonical flow is **Choose package → View listed scope & amount → Review and e-sign NLN service agreement → Secure Stripe Checkout → Webhook-verified payment → Project onboarding**.

- /pricing advertises exactly three current one-time website bundles: Basic Website $599, Business Website $799, Business Growth Plus $999.
- /start?package=Basic%20Website renders the e-signature package agreement and fixed upfront amount.
- /api/packages returns the trusted server-side package table, exactly matching checkout.js.
- /api/checkout/start writes the accepted package, electronic signature, agreement version/hash and price to nln_service_orders (separate from lead records). Card payment cannot start before the agreement is recorded.
- Stripe Checkout Sessions are created on the backend only, with amount from the server package table and an order ID stored in Stripe metadata. No client-supplied amount is trusted.
- /api/stripe/webhook verifies Stripe-Signature on the raw body, then marks the matched order paid ONLY when the signed paid event includes the correct matching session and amount.
- /api/payment-status checks the Stripe session and verified database record; /order-confirmation never labels an order paid from the browser redirect alone.
- /admin shows inquiries and signed package order/payment statuses.

**Do not turn on live charges until the merchant approves final agreement terms, cancellation/refund policy and account branding; verifies NLS Stripe account use, receives/sets a Stripe API secret & webhook secret privately in Render; and completes a test-mode purchase + signature validation.**

Current gates:
- CHECKOUT_ENABLED=false (must be explicitly enabled via secure Render configuration)
- AGREEMENT_APPROVED=false (must be explicitly enabled when owner approves agreement)
- STRIPE_SECRET_KEY (not present; never write to GitHub)
- STRIPE_WEBHOOK_SECRET (not present; never write to GitHub)
- SITE_URL must be the verified live HTTPS domain before enabling charges

If payments aren't configured, the system saves the signed agreement and displays a truthful next-step confirmation instead of attempting to charge or falsely claiming that checkout succeeded. The site stays noindex until separate public SEO go-live review.

The existing general contact form is for questions/custom work. Published package sales should route through /pricing and /start instead of free quotes.

## First unified Marketplace pilot (2026-11-21)

The homepage now prominently serves two audiences with separate working paths:
- \`/find-a-pro\` – **customers** submit a service category, service ZIP, timeframe, contact details, and job description.
- \`/join-as-pro\` – **professionals** submit business details, selected trade categories, served ZIP codes, and verification information.
- \`/pricing\` / \`/start\` – **business services** retain the existing fixed-price packages and e-signature-before-payment flow.

The original separate \`nln-preview/app.html\` remains an interactive **demo only**, not a shared real-user provider dashboard.

### What genuinely works
- New shared Postgres tables \`nln_marketplace_requests\`, \`nln_marketplace_providers\`, \`nln_marketplace_matches\`, separate from legacy \`leads\` and website package purchases.
- POST \`/api/marketplace/request\` validates the service request and safely saves it; new requests are \`NEW\`.
- POST \`/api/marketplace/provider\` validates and saves applications; new applications are \`PENDING\` and are **not listed as approved**.
- All matching queries are private, restricted to administrators, and only consider \`APPROVED\` providers whose trade **and ZIP code** match.
- Authorized administrators review business documents/qualification details, record a meaningful verification note, approve or reject applicants, and can record internal candidate matches.
- Customer and pro submissions do not create Stripe charges, paid leads or subscriptions. Search indexing remains off until production launch.

### Not yet implemented
- Identity verification automation, self-service provider login, instant lead alerts, customer/pro messaging, job completion tracking, customer ratings or automatic lead charges.
- Recording a potential match in the admin inbox **does not notify either party or indicate the job was booked**.
- Customer and pro applications are not silently shared publicly. The privacy notice describes the limited data processing and future contact with vetted professionals.
- A public searchable directory requires verified real providers, explicit publication consent and more controls.

### Pilot manual process
1. Receive one legitimate customer request and a compatible provider application for the same ZIP/trade.
2. Independently verify the professional's business identity, relevant licensing/insurance where required and contact details. Record an admin verification note.
3. Mark the provider \`APPROVED\` in the protected NLN command center.
4. Match the customer request to the approved provider and **manually** contact both sides for permission and job scheduling.
5. Record job outcome manually until provider login, automated messaging and completed-job status are developed.
